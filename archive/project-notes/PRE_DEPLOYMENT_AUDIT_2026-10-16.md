# ART NEXUS — Pre-deployment structural audit

**Audit date:** 16 October 2026  
**Mode:** Non-destructive, diagnostic-only review  
**Scope:** `src/app.src.html`, built `index.html`, project tree, README/checkpoint notes, and existing regression suites.  
**Code changes at audit time:** None. This was a pre-production diagnostic snapshot taken before the later production integration and current UI refinements.

> The following verdict and inventory are historical. For the current production code, local tests, and outstanding release gates, see `PRODUCTION_UPGRADE_IMPLEMENTATION_REPORT_2026-10-16.md` and `PRODUCTION_READINESS_GAP_REVIEW_2026-10-16.md`.

> **Executive verdict: NOT READY for public marketplace, payments, or accounts.** The repository describes a local-preview prototype and contains no serverless API implementation, database, payment provider, authentication service, or deployment/CI configuration. It can be deployed as a static demo if clearly labelled; it must not be represented as a functioning marketplace or secure account system.

## Verification performed

- Ran `node tests/regression_v4.cjs && node tests/regression_v6.cjs && node tests/regression_v7.cjs` — **all passed**.
- Read-only HTML checks: source and built app each have **270 unique IDs**, no duplicate IDs, and no unresolved ARIA ID references.
- No browser-based performance trace, cross-device visual QA, accessibility audit, live API test, or payment-provider test was run.
- Important: the existing V6 suite still asserts the former in-profile recommendation scroll behavior. Passing it does **not** verify the latest Explore More transition request.

## 1. Animation performance & visual compliance

| Audit item | [CURRENT STRUCTURAL STATE] | [CRITICAL LACKING ELEMENTS & VULNERABILITIES] | [RECOMMENDED PRODUCTION UPGRADES] |
|---|---|---|---|
| **1.1 Splash / “500x cinematic zoom”** | • The alleged 500× logo zoom and 2-second onboarding zoom loop are not present. The active welcome is a post-gate artwork-tile collage.  • `welcomeArtJourney` runs for **3,880 ms**; the handoff timers reveal the message at 1,550 ms, apply the whiteout at 2,650 ms, begin final reveal at 3,300 ms, and finish at 4,000 ms.  • Tiles animate from scale `0.06` to `3.2`; CSS animates `left`, `top`, `opacity`, `transform`, and `filter` (`src/app.src.html:589–623, 9,660–9,663`).  • Reduced-motion rules disable the tile animation. | • `transform` and `opacity` are generally compositor-friendly; **`left`/`top` cause layout work**, and animated blur/brightness filters plus large shadows can trigger expensive paint/compositing.  • `will-change: left, top, opacity, transform, filter` can reserve layers and GPU memory for many tiles.  • Static inspection cannot establish frame pacing, texture tearing, thermal impact, or 60/120 Hz performance. | • If retaining the visual, move the travel path to `translate3d()`/transform-only animation and keep opacity composited.  • Avoid animating blur/brightness; prepare softened imagery before the transition.  • Limit active layers, shadow area, and `will-change` lifetime.  • Profile low/mid-tier iOS and Android devices at 60/120 Hz; test reduced-motion and short/tall viewports. |
| **1.2 Muted ambient diffusion / “blur-[120px]”** | • There is **no 120px blur**. The source uses a 6px landing-art blur, 7px tile blur, a 16px endpoint tile blur, 14–16px backdrop filters, and a **28px full-canvas blurred artwork backdrop** (`src/app.src.html:390, 600–622, 1,999–2,000, 2,085–2,098`).  • Artwork backdrops are absolutely positioned and `pointer-events:none`; the app viewport clips overflow. | • The current layout isolates the backdrop from pointer hit-testing and normal feed flow, but a full-viewport blur still has GPU fill-rate and memory cost. Repeated `backdrop-filter` surfaces may compound over the artwork viewer, sheet, and feed badges.  • No device-level scrolling-latency or paint profiling exists. | • Benchmark the art viewer and masonry feed on constrained GPUs, checking scrolling while overlays open/closed.  • Prefer a pre-blurred, downscaled backdrop image or gradient where visual fidelity permits.  • Keep blur layers scoped to the active overlay; use paint containment only after validating stacking/focus behavior.  • Add performance budgets and trace-based regression checks. |
| **1.3 Folio Stack zero-spacing / image stability** | • The lightbox uses a vertical scroll container with `scroll-snap-type: y proximity`. Slides are `display:block`, `margin:0`, `padding:0`, `border:0`, `line-height:0`; images are also `display:block` (`src/app.src.html:3431–3435`).  • Cover and ordered slide data are stored separately as `image` plus `folio_slides`; the cover is first, slides follow. Later slides are lazy-loaded. | • Block-level images and zero line-height remove the common inline-image baseline gap; the zero-gap layout is structurally sound.  • Image dimensions/aspect ratios are not declared on the generated `<img>` elements. Variable-ratio or lazy-decoded slides can still shift scroll positions and snap alignment.  • Single-file base64 images increase memory and local-storage pressure. | • Persist validated width/height metadata and reserve intrinsic aspect ratios before decode.  • Test mixed portrait/landscape stacks, lazy-loading boundaries, browser zoom, and scroll-snap on physical devices.  • For production, move original assets out of localStorage to object storage/CDN and deliver responsive variants. |

## 2. Architecture & data management

| Audit item | [CURRENT STRUCTURAL STATE] | [CRITICAL LACKING ELEMENTS & VULNERABILITIES] | [RECOMMENDED PRODUCTION UPGRADES] |
|---|---|---|---|
| **2.1 Commission Slot Governor** | • Cap is five. The number input has `min=0`, `max=5`, `step=1`; loading clamps saved values to 0–5, saving requires an integer in range, and the +/- helper clamps the value (`src/app.src.html:4,871–4,876; 5,437–5,441; 5,538–5,562`).  • Accepting a commission decrements with a floor of zero; slot persistence is attempted before queue status is committed, with rollback paths on local save failure (`5,768–5,800`).  • The profile availability badge is visible only when intake is open and slots are positive. The public CTA is intentionally non-blocking and gives a local status toast when closed/full (`5,566–5,594`). | • The basic integer boundary is correctly enforced in the prototype; no normal UI path should produce negative or >5 values.  • `changeCreatorCommissionSlots()` accepts a generic `delta` without validating it as an integer, though the current buttons only pass ±1.  • The public CTA hardcodes **“Commissions Full (5/5 Slots Taken)”** for any unavailable state, including a paused intake with remaining slots; that is misleading.  • localStorage read-modify-write is not atomic across tabs/users; duplicate accepts can race in production. No server reservation or durable audit trail exists. | • Keep a server-authoritative integer constraint (`0 <= available_slots <= allocation`) and atomically decrement/reserve in a database transaction with idempotency and optimistic locking.  • Derive public copy from the actual state: paused vs zero slots vs open.  • Validate `delta` and every state transition at the service boundary, not just the UI.  • Add concurrent-accept and persistence-failure tests. |
| **2.2 Proposal / order-brief intake and sanitization** | • Commission inputs cap client name at 80, title at 100, budget at PHP 1–100,000,000 with integer step, usage rights at 240, and scope brief at **500** characters (`src/app.src.html:4,312–4,316`).  • Submit logic repeats length cleaning and checks required values, integer budget, and queue cap. Local queue normalization applies the same broad bounds; rendered text fields are HTML-escaped (`5,679–5,683; 5,598–5,620`).  • Creator bio is capped at **600**, not 140 (`4,791–4,792`). There is no current 140-character bio constraint. | • All validation is client-side and local; DevTools/localStorage can bypass it. `cleanPlainText()` removes control characters and clips length but is not a full schema validator.  • Queue IDs are cleaned but not restricted to a safe ID grammar, then HTML-escaped into inline JavaScript handler strings. HTML entity escaping is not JavaScript-string escaping after HTML parsing; untrusted imported/tampered records could create a persistent DOM-XSS surface.  • There is no server-side rate limit, spam control, identity/consent verification, or audit trail. | • Confirm the actual product limit before changing the 500-character brief / 600-character creator bio; **the requested 140-character rule is not implemented**.  • Use a server schema with strict types/ranges, length limits, Unicode normalization, validation errors, rate limits, and abuse controls.  • Replace inline `onclick` handlers with event delegation and opaque allowlisted IDs; validate every loaded record.  • Keep text in `textContent` where practical; use context-appropriate escaping and a restrictive CSP. |
| **2.3 Folio Stack ingestion and local cache** | • Upload accepts JPEG/PNG/WebP/GIF up to 15 MB, decodes through browser `Image`/canvas, and tries resized JPEG outputs at 1,400/1,100/900/720px with decreasing quality until within the data-URL limit (`src/app.src.html:8,150–8,180`).  • Per-image cap is 420,000 characters; total works cap at eight; stacks allow up to eight total images (cover plus up to seven slides); work JSON is capped at 3.8M characters. Duplicates and cover repeats are filtered during normalization (`5,260–5,330; 8,355–8,380`).  • A single asset is `image`; a stack is `image` plus ordered `folio_slides`. Creator data is persisted in localStorage. | • Ingestion is a single-browser cache workflow, not cloud storage or a durable media pipeline. localStorage is synchronous, quota-limited, user-editable, and can be cleared by the browser.  • Converting all formats to JPEG is lossy and drops transparency/animation. Base64 adds storage overhead; multiple 420k images can pressure memory and storage.  • There is no virus/content inspection, EXIF privacy scrub assurance, upload moderation, object ownership policy, or CDN derivative pipeline. | • Use server-issued upload authorization and object storage with size/type verification, malware/content scanning, EXIF removal, moderation, and immutable asset IDs.  • Keep metadata and slide order in a database; enforce per-creator quotas server-side.  • Generate responsive AVIF/WebP/JPEG variants and preserve source originals when licensing permits.  • Test storage quota, retry, interrupted upload, image decode failures, and concurrent editing. |

## 3. Full-stack dispatch & security

|---|---|---|---|
| **3.1 Marketplace checkout and order state** | • Cart validation checks item type, listing status, duplicate Originals, and local print stock. | **3.2 GCash/Maya, card mock, and delivery tiers** | • Wallet UI asks for a 10-digit number beginning with 9; a passing regex sets `walletVerified=true` and explicitly states no provider was contacted (`src/app.src.html:10,780–10,794`).  • Card fields are only locally checked with Luhn/expiry/name/CVC rules; no processor call is present (`10,797–10,861`).  • Delivery fees are fixed: Metro Manila ₱350, provincial air cargo ₱650, Baguio/CSDA pickup ₱0 (`10,538–10,542`); fee is calculated from a radio selection (`10,661–10,675`). | • This is a format check, not wallet ownership or payment verification. | **3.3 Role authorization, local sessions, and scope locks** | • My Profile uses email-only local profile lookup. Optional same-origin adapters are documented, but no service implementation is in this repository. | • UI visibility is **not authorization**. localStorage, role, email, UUID, stock, and portfolio can be modified by the user. There are no secure cookies, signed tokens, server-side ownership checks, or enforced Creator/Collector policies.  • Optional `/api/profile?id=…`, `/api/social/follow`, and Creator registry calls require a real backend to enforce authentication, authorization, CSRF protections, validation, and durable storage. ID-only profile lookup could become an IDOR if a backend trusts the supplied ID.  • Account email and activity data are readable by same-origin JavaScript and exposed to any successful XSS. | • Implement an identity provider or secure server session before public sign-in; derive role/ownership from server-side records, never from localStorage.  • Authorize every read/write and object access on the server; use CSRF defenses, rate limits, audit logs, secure cookie settings, and strict input schemas.  • Minimize stored PII and define retention/deletion/export policy.  • Add tests for cross-account access, privilege escalation, IDOR, and forged Creator state. |

## Bottom line

ART NEXUS is a visually structured **local prototype**, not a deployable full-stack marketplace. Existing regression tests pass for the prior behavior, but the requested recent UI changes are **not implemented** in either `src/app.src.html` or the current built `index.html`. No app source, built app, tests, or architecture files were modified during this diagnostic-only audit; only this report was created. Populate collaboration contacts only after receiving verified artist emails; do not use generated ID-based addresses.
